Folder & File Compare Tool — Concept

Working title “Parallax”. A fast, cross-platform (Windows + Linux) side-by-side compare tool in the spirit of Beyond Compare, where folders, archives and Git revisions are all just sources that can be compared against each other.

TL;DR

Concept: One virtual-file-system layer turns a local folder, a .zip/.7z/.tar.* archive, a Git branch, tag or commit, and a Git working tree into the same kind of browsable tree. The compare engine and both views (folder and text) only see that tree.

Tech stack: a Rust core (gitoxide, libarchive/zip/7z crates, imara-diff, tree-sitter, rayon) with a thin UI. Recommended UI: Tauri 2 with a virtualized web front end. Fallback if Linux rendering speed falls short: Qt 6/QML via CXX-Qt.

Existing tools: Beyond Compare 5 comes closest but has no native “Git ref as a folder” source. DirectCompare, a newer commercial tool, advertises nearly this exact feature set. Evaluate both before building anything (see §3).

1. Requirements → design decisions

RequirementDesign decision
Local app for Windows and LinuxA native binary with no JVM or .NET runtime. Ships as MSI and portable ZIP on Windows, and as AppImage, .deb/.rpm and Flatpak on Linux. A CLI entry point (parallax a b) so the app can serve as git difftool/mergetool.
Performance is importantAll heavy work (walking, hashing, diffing, decompression, Git object access) runs in a multi-threaded Rust core. The UI only renders the visible viewport. Results stream in while the compare is still running, and every operation can be cancelled.
Side-by-side view like Beyond CompareTwo-pane folder tree with a status gutter and aligned rows; a two-pane text view with aligned lines, inline highlighting of changed characters, an overview strip and a line-detail pane; sessions in tabs.
zip / 7z / … usable in folder compareAn Archive provider in the virtual file system (VFS). An archive expands like a folder, including archives nested inside archives. Where the archive stores size and CRC per entry, files are compared from those headers without decompressing anything.
Git repo usable in folder compareA Git provider in the VFS exposes the working tree, the index, and any ref or commit as a read-only tree, read directly from the object database without a checkout.
Folder/file compare between Git branchesBranch A vs. branch B is simply two Git sources. Options: direct compare (A..B) or “what B changed since it branched off” (merge-base, A...B). Identical tree hashes skip whole subtrees.
Syntax highlighting for common filestree-sitter grammars in the core (C/C++, C#, Java, JS/TS, Python, Rust, Go, JSON, YAML, XML/HTML, CSS, SQL, Markdown, shell, PowerShell …), with a TextMate-grammar fallback (syntect) for the long tail. Only the visible text is highlighted.

2. Feature scope

MVP

  • Folder compare: any source vs. any source (local, archive, Git ref, Git working tree)
  • Compare levels: structure → size/date → CRC/hash → byte-exact → rules-based (ignore whitespace, line endings, case, encoding)
  • Filters: show all / differences / same / orphans; include/exclude masks; honour .gitignore
  • Actions: copy left→right and right→left, delete, sync preview (Git refs are read-only; “restore into working tree” instead)
  • Text compare with syntax highlighting, inline character highlighting, an overview strip, next/previous difference, editing and saving
  • Encodings (UTF-8/16, Windows-1252 …) and line endings (CRLF/LF) detected and shown
  • Binary detection with a hex compare fallback
  • CLI plus git difftool -d / mergetool integration; saved sessions

Later

  • 3-way text merge (with Git conflict resolution) and 3-way folder compare
  • Commit-range picker, “compare with stash”, Git LFS pointer resolution, submodules as nested repos
  • Image compare, table/CSV compare, office documents converted to text
  • Structural (AST) diff mode, like difftastic; “ignore comments” rule
  • Reports: HTML and patch export
  • Remote sources: SFTP, S3, WebDAV
  • Plugin API for custom VFS providers and file converters

3. Is there an existing tool that matches this?

Short answer: none of the established tools covers everything. The gap is Git revisions as first-class folder sources, especially combined with archives and Linux support. Recommendation: before investing in development, run a one-day evaluation of Beyond Compare 5 (with a git worktree or difftool -d script for branches) and DirectCompare against your real repositories. Build your own tool only if neither passes. The strongest case for building is an open-source, Git-native, Beyond Compare-class tool: that niche is currently empty.

The key idea is quick_id: each provider can return a cheap content fingerprint that does not require reading the file. Local files return size and mtime. Zip and 7z entries return the stored CRC32 and size. Git entries return the blob or tree hash. The compare engine uses the strongest fingerprint both sides share and falls back to reading content only when it has to.

6. Performance strategy

Folder compare

  • Parallel walk of both sides (jwalk/ignore crates); results stream into the UI as they arrive.
  • Git vs. Git: identical tree hash ⇒ the whole subtree is identical, so it is skipped without being walked. Identical blob hash ⇒ the file is identical. Comparing two branches of a large repo with a small diff costs about as much as the diff itself, not the repo size.
  • Git vs. local file: compute the Git blob hash of the local file (honouring autocrlf and filters), or reuse the stat cache in Git's index the way git status does.
  • Archives: compare the stored CRC32 and size from the headers. Decompress only when the CRCs differ and a rules-based compare is requested.
  • Local vs. local: size → mtime → memory-mapped byte compare with early exit, or xxh3 with a persistent cache.
  • Lazy expansion: collapsed folders are compared in the background at low priority.

Text compare

  • Memory-mapped input with a line index built in parallel. Lines are interned and hashed before diffing.
  • imara-diff (histogram algorithm), the fast diff engine also used by gitoxide and the Helix editor; Myers as an option.
  • Intraline (character/word) diff computed only for visible changed lines.
  • Syntax highlighting with an incremental tree-sitter parse, limited to the viewport plus a margin and capped by a time budget. Above a size threshold, highlighting is switched off automatically.
  • Binary or very large files fall back to a chunked hex compare.

Decision gate (week 2): build a Tauri spike that scrolls a 1M-line aligned diff and a 200k-row tree on Ubuntu (WebKitGTK) and Windows (WebView2). If Linux falls below ~50 fps, switch the UI to Qt/QML via CXX-Qt. The Rust core stays unchanged either way, because it is UI-agnostic.

9. Risks & open questions

Risks

  • WebKitGTK performance on Linux → mitigated by the week-2 decision gate and the UI-agnostic core.
  • Solid 7z archives must be decompressed sequentially → compare by header CRC first, then extract once into a cache.
  • Git edge cases: autocrlf/eol attributes, clean/smudge filters, LFS, submodules, sparse checkouts, very large packfiles.
  • Malicious archives (zip bombs, path traversal) → size and ratio limits, path sanitising, fuzzing.
  • Scope creep: Beyond Compare has had 25+ years of polish. Keep the MVP focused on the three source types.

Open questions

  • Open source or commercial? This decides the Qt licensing question and how you compete with Beyond Compare and DirectCompare.
  • Is writing into archives (updating a zip) needed, or is read-only enough?
  • Is macOS desired later? The stack supports it at little extra cost.
  • Which file types beyond code matter (Office, PDF, images)?
  • Is 3-way folder merge needed, or only 3-way text merge?
